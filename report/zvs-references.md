# ZVS Scan — Reference Content & Regression-Gated Baseline

This document explains how the ZVS 2018 content scanner separates **genuine
prose** from **lexicographic reference content**, and why the current scan is
wired as a **regression gate** rather than an absolute "zero violations"
check.

Companion files:

- `report/zvs-baseline.json` — committed baseline (flat
  `source\0rule_id\0forbidden -> count` map) of the current clean corpus.
- `report/zvs-scan-<date>.json` — full machine-readable scan (gitignored).
- `report/zvs-scan-summary.md` — human-readable scan summary (gitignored).
- `scripts/zvs/scan_content.py` — the scanner + gate.

---

## 1. Reference content is lexicographic, not prose

The wiki contains large tables that **document** deprecated → preferred forms
rather than using the deprecated forms in running Zolai prose. These are
**reference corpora**, not product prose, and are intentionally not repaired:

| Path / pattern | Type | Why it stays |
|---|---|---|
| `vocabulary/` | Bilingual lexicon / word lists | Lexicographic entries pair a deprecated form with its ZVS-2018 preferred form (e.g. `ram` → `gam`). Each entry lists both forms by design. |
| `vocabulary/generated/` | Auto-generated word lists (`vocab_a.md` …) | Machine-extracted lexicon sets; same lexicographic purpose. |
| `grammar/forbidden_stems_auto.md` | Auto-synced stem-mapping table | Generated by the `check_stems.py` auditor; lists Stem-I + `na` nominalizations versus their Stem-II + `na` corrections. It exists precisely to enumerate the incorrect form. |
| `grammar/verb_stems.md` | Human-edited stem mapping | Documents Stem I vs Stem II verb forms, including example sentences that intentionally show both a deprecated and a corrected form side by side. |
| `bundle/03_negation_particles.md` (STEM_* rows) | Reference stem table section | A stem-mapping table embedded in a grammar note; its `STEM_*` rows document forms rather than use them. |

The scanner flags a cosmetic `reference` triage bucket for content under
`vocabulary/`, `*_auto.md`, and the stem-mapping tables (see
`_is_reference_source()` / `_triage_bucket()` in `scan_content.py`). This
bucket is **only** used in the human summary — it is **never** consulted by the
regression gate. Reference content stays in the corpus and is not edited.

## 2. No broad `suah` exception

`suah` (DIALECT_08, deprecated → `chuak`) is the single largest violation
token — **606 hits across 247 (source, rule, token) combos** in the current
scan. Almost every hit lives in reference content:

- ~600 of the 606 hits are under `vocabulary/bible_context/*` (Bible verse
  grammar studies, which quote source text verbatim) and
  `vocabulary/generated/` (extracted lexicon entries).
- Only a handful fall under genuine-prose paths, and none are in high-volume
  modern prose files.

A broad `suah` exception was deliberately **not** added:

- It would disable `DIALECT_08` globally, allowing future genuine prose
  regressions to `suah` to slip past the gate silently.
- The regression baseline already captures every existing `suah` combo, so a
  committed exception would add no signal — it would only remove the ability
  to catch **new** `suah` regressions.
- The rare genuine-prose `suah` hits baked into the baseline remain visible in
  `report/zvs-scan-summary.md` for future triage; they are not hidden, just
  not gate-blocking as "pre-existing."

Rule: add a specific exception only when a token is a **function word or
universal particle** (see `DEFAULT_EXCEPTIONS`); keep dialect word-replacements
such as `suah` gated so new regressions are caught.

## 3. Regression-gated design rationale

The scan is **report-only by default** and exits `0` always. In CI it runs with
`--gate` against the committed baseline:

```
python scripts/zvs/scan_content.py --wiki --gate --baseline report/zvs-baseline.json
```

The gate is **backward-looking by design**: the baseline captures the current
clean corpus (after the wiki prose fix), and the gate fails **only** when a
`(source, rule_id, forbidden)` combo is:

- **NEW** — not present in the baseline at all, or
- **INCREASED** — its current count exceeds the baseline count.

Existing violations at or below their baseline count never fail. This gives us:

- **No endless toil on pre-existing reference debt.** The 1,150+ pre-existing
  violations (overwhelmingly lexicographic reference content and quoted Bible
  text) are baked into the baseline once, then ignored.
- **Real regression protection.** Any new deprecated form introduced into
  genuine prose — even a single hit in a previously-clean file — trips the gate
  and blocks CI.
- **Zero per-source classification code.** Reference content is auto-excluded
  simply by having been captured in the baseline; no rules list, no source
  allow-listing, no drift between "what is reference" in code vs. reality.
- **Cost-free to evolve.** When reference content is fixed or the corpus is
  cleaned, regenerating the baseline re-bakes the improved state.

Because the gate compares **counts between builds**, it also catches when an
existing deprecated form is *introduced into a new file* (a new source combo)
or *spread further* (a higher count in a known file).

## 4. Genuine prose fixes applied

Beyond the baseline bake, one round of real prose fixes was applied and
committed to `zolai-wiki` (`cc4698c`, "fix(zvs): correct hi leh to hihleh in
prose"):

- **4 instances** of `hi leh` → `hihleh` (DIALECT_16, conditional-particle
  deprecation) in genuine grammar prose:
  - `bundle/01_language_guide.md` — 2 fixes
  - `Zolai_Standard_Format.md` — 2 fixes

These were the only clearly-genuine modern-prose violations worth repairing in
the initial triage; the rest of the reported corpus is reference/lexicographic
or quoted historical text.
